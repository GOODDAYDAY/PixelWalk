# 投稿与审核逻辑

[English](../en/moderation.md) · [README](../../README.md)

## 谁在审核

内容审核由人完成，没有接入 AI 图像审核、OCR、政治内容识别或敏感词自动放行机制。社区可以反馈，但投票数不会自动批准作品。只有仓库 write / maintain / admin 协作者的命令生效；read、triage、普通用户和作者本人的指令不生效。代码允许 admin 自审，这是明确的权限例外，建议实际运营仍交叉审核。

## 投稿表单

使用「风景投稿」模板，保留中文字段名：作品名称、像素 PNG、展示时段、体积、摆放方式、素材来源、确认。标题会去掉控制字符和尖括号、压缩空白并截到 40 个字符。来源与许可必须填写，两项确认必须勾选。表单仍为中文；英文文档提供字段对应关系。

只接受一个 GitHub 附件图片地址。提交文件须 ≤1 MiB（1,048,576 字节）、160×160、8 位 RGBA 或带调色板的非交错 PNG，非动图，有实际可见像素且至少 1% 透明像素。程序检查 PNG 结构、CRC、解压大小、透明度并重新编码；剥离元数据，把透明度按 128 阈值变为全透明/全不透明。所有下载与重定向在请求前检查 HTTPS 和 GitHub 域名，并限制次数、时间与大小。格式校验不能判断内容是否合规。

## 维护者操作

先查看图片、名称、素材来源、许可及链接，再对照[内容规范](content-policy.md)逐项判断；有疑问就退回，不要先批准等上线后再处理。

- `/approve`：检查权限后重新读取当前 Issue，确认未关闭且仍有 `scenery` 标签。读取最新表单、校验图片、存入 `scenery/images/gh-编号.png`，向 manifest 写入 `queued`、审核人、时间、来源和图片 SHA-256；添加 `approved`，移除待审/待修改标签。Git 提交成功才算快照持久化。
- `/reject 理由`：对未进入发布候选的投稿退回修改，删除已有排队快照、移除 `approved` / 旧 `accepted`，添加 `needs-changes`，说明问题。它不自动关闭 Issue，也不删除原 Issue 附件。
- 普通评论被忽略；命令不区分大小写，可有前后空白。PR 评论不参与管线。只有个人 `User` 账号可投稿。

已排队后编辑 Issue 不会改变快照，维护者需重新 `/approve`。审核失败不会自动撤掉此前已批准的快照；如要阻止旧快照发布，应先 `/reject` 再修改。仅关 Issue 或手动改标签不能取消队列。已进入发布候选的 `published` 记录无法用 `/reject` 下架，详见[投放与下架](publishing.md)。

## 标签与故障

`scenery` 投稿类型；`pending-review` 待审；`needs-changes` 待修改；`approved` 已保存候选；Issue 的 `published` 表示部署成功后的发布确认。旧 `accepted` 标签不驱动队列。实际队列依据 manifest，不依据点赞或标签。

Actions 与 Issue 标签/评论不是数据库事务。若标签或评论成功而 Git 提交失败，可能短暂不一致；必须查看运行日志和 manifest，不能只看“审核通过”评论。解决失败后重新审核。403、写接口 404、下载/格式异常会阻止正常完成；删除不存在的标签与查询不存在的协作者允许返回 404。
