# PixelWalk 部署与社区审核建议

日期：2026-10-15（Asia/Shanghai）。公开源代码仓库：JilinJL/PixelWalk。本文描述当前原型的上线选择，不表示服务器或域名已部署。

## 推荐第一步：GitHub Pages + GitHub Issues

当前项目完全静态。图片在浏览器处理，草稿与本地审核结果保存在 localStorage，不消耗服务器硬盘，也没有多人共享的投稿数据库。

建议先用 GitHub Pages 托管游戏，以 Issues 收集用户手动附上的像素 PNG，由社区评论和投票、维护者决定收录。暂时不增加图片服务器、数据库或自动抠图服务。公网体验仍需在目标用户网络实测。

已提供部署工作流 `.github/workflows/pages.yml`，main 分支推送后自动发布，也支持手动重试：

1. 仓库 Settings → Pages → Build and deployment → Source 选择 GitHub Actions。
2. Actions → Deploy GitHub Pages → Run workflow，在 main 上运行。
3. 以部署输出 URL 为准；预计项目地址为 https://jilinjl.github.io/PixelWalk/。

工作流先测试，构建 `dist/`，再通过官方 Pages Actions 发布。普通推送 / PR 运行 Check，main 推送额外触发 Pages 部署。发布包只复制运行代码和 assets，不包含 docs、tests、work 或离线单文件。

## pixelwalk.online

域名和服务器不是必须绑定在一起。注册后可以把 `pixelwalk.online` 直接绑定 GitHub Pages；不必先指向自己的服务器 IP。

先在 GitHub 账户设置中按官方指引验证域名，再到仓库 Pages 设置自定义域名，按当时 GitHub 给出的 apex DNS 记录配置，等待 DNS 与证书生效后启用 Enforce HTTPS。使用 www 时可配置 CNAME 到 jilinjl.github.io，不能把项目子路径写入 DNS。当前尚未注册、验证或写入自定义域名，发布包也没有提前加入 CNAME。

## 图片多了怎么办

不要把公开 Git 仓库或 Issue 附件当作无限图片存储 / CDN。GitHub Pages 的发布站点上限为 1 GB、软带宽限制为 100 GB/月；只在版本中收录精选小图，数量上来后改对象存储。

按每件最终 PNG 20–50 KB 估算（示例，不是对所有图片的实测）：1 万件约 200–500 MB；若长期保存每张 8 MB 的原图，1 万张约 80 GB。需要限制的是原图留存、数量和请求流量，而不只是更换网页托管。

未来可用 `GitHub Pages 前端 + 轻量 API + 对象存储`。自己的服务器只处理权限、元数据和任务，图片通过限额的签名上传直达存储；原图定期过期，正式图按需加载并缓存。国内用户为主时，优先实测国内 OSS / COS 与海外方案的访问速度和总费用，再决定供应商。

备选 R2 Standard 截至查询时提供每月 10 GB-month、100 万次写类操作、1000 万次读类操作免费额度，公网出站不计流量费；超额存储 $0.015/GB-month，读写操作另计费。免费额度不是硬性消费上限。

来源：
- https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits
- https://developers.cloudflare.com/r2/pricing/

## 自有服务器仍可部署

`npm run build:site` 得到的 dist 可直接交给 Nginx 静态托管；这一原型本身不需要 Node 常驻、数据库或图片上传目录。以后即便前端继续放 Pages，也可以单独把 API 部署到自己的服务器，图片走对象存储。

本轮不修改服务器、DNS 或域名账户。旧开发文档是完整产品设计基线，不是已实现功能清单。当前尚无 GitHub OAuth、远程管理、共享投稿库、自动抠图、自动收录 / 发布管线。
