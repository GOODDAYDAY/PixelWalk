# Automated publishing, deployment, and recovery

[中文](../zh-CN/publishing.md) · [README](../../README.md)

## Pipeline

1. `scenery-review.yml` handles new comments on scenery Issues using main's code. Authorized human review commands validate and commit PNG snapshots and manifest entries to main; ordinary comments do nothing.
2. `scenery-publish.yml` checks main at minutes 7 and 37 of each UTC hour. You can also select Actions → Scenery publish → Run workflow, with main as the branch.
3. `batch` promotes every `queued` entry to manifest `published`, generates `content.js`, runs tests, and commits/pushes. This manifest state means included in a deployment candidate; it alone does not prove the website is live.
4. `deploy` calls reusable `pages.yml` with the batch commit SHA, reruns tests, builds dist, uploads the Pages artifact, and deploys. Pushes made with `GITHUB_TOKEN` do not trigger ordinary push workflows, so deployment must be called explicitly.
5. Only successful deployment enables `announce`: remove `approved` / legacy `accepted`, add the Issue's `published` label, post a uniquely marked publication comment, close the Issue, and commit `announcedAt`. The Issue label is a post-deployment acknowledgment.

Ordinary main pushes trigger Check and Pages. An ordinary Pages job checks out current main when starting, reducing the risk of queued old push events rolling back the site. Manual Pages/publishing jobs are restricted to main. Do not use manual ref parameters to bypass branch restrictions. `dist/` contains runtime files, assets, and candidate/published scenery images, excluding docs/tests/work. The standalone HTML is separately generated by `npm run build`.

## Permissions and concurrency

| Workflow | Required permissions |
| --- | --- |
| Check | contents: read |
| Scenery review | contents: write; issues: write |
| Scenery publish | contents: write; issues: write; pages: write; id-token: write |
| Pages | contents: read; pages: write; id-token: write |

All use the repository `GITHUB_TOKEN`. No extra PAT, AI credential, or image server is required. A read-only repository default does not prevent explicit workflow permission requests. Review and publishing share the `scenery-git` lock, held through deployment and notification. Pages has its own `pages` lock. Neither cancels running work; `queue: max` permits up to 100 waiting entries, with excess entries still subject to cancellation. Inspect Actions instead of assuming unlimited queuing. The push script attempts five times with rebase; unresolved conflicts fail rather than overwrite manual changes.

## Failure recovery

The previous implementation lost the retry path after promoting a batch before failed deployment. Now every manifest `published` entry without `announcedAt` remains pending. The next run retests, redeploys, and retries notification even if no new submissions were queued.

Notification deduplication checks bot comments for `pixelwalk-published:N`. Only completed label/comment/close operations produce `announcedAt`. A later failure may temporarily leave partial Issue state, but retrying does not repeat an existing marked comment. If the final progress commit fails, comment markers support recovery on the next run. Do not invent acknowledgment timestamps to hide pending work.

Open a failed run and distinguish review/API, Git push, build, Pages, and notification failures. Fix the underlying permissions/conflicts/files, rerun Scenery publish on main, and verify public assets, Issues, and manifest state. If a review comment exists but its snapshot push failed, repeat review first.

Scheduled Actions are best-effort: runs can be delayed/dropped, or stop due to inactivity/account conditions. Absence of runs is not evidence of approval. See [GitHub troubleshooting](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows), [concurrency queues](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency), and [GITHUB_TOKEN behavior](https://docs.github.com/en/actions/concepts/security/github_token).

## Withdrawal and removal

- `queued`: use `/reject reason` and verify the successful push. Closing the Issue alone is insufficient.
- Candidate/published: `/reject` cannot remove it. Wait for in-flight publishing, remove the manifest entry and `scenery/images/gh-N.png`, regenerate with `node scripts/scenery.cjs content`, run tests and the site build, review and commit to main, wait for Pages success, then remove the Issue's `published` label and explain the result. Do not leave a dangling image reference.
- For urgent removal, pause publishing and handle in-flight deployment first so an old artifact cannot restore the content; resume afterward. Git history and original Issue attachments require separate platform removal when necessary.

## Verification limits

Mocked API tests do not prove real token write capabilities. Verify tests, snapshot push, Pages deployment, public image availability, and Issue updates separately. An empty-queue run skips deployment/notification and is not an end-to-end publication test. See the [audit report](../automation-audit.md) for actual evidence.
